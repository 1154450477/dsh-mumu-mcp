## 1. 项目定位与设计哲学

**定位**：把 MuMu 模拟器里的一台安卓机封装成 21 个 MCP 工具（`mcp__mumu__mumu_phone_*`），交给 DSH（dsh-mcp-client）宿主的 Agent 使用，让 AI 像真人一样玩手机——看画面、点按钮、打字、刷视频、玩游戏；并通过本地控制口与 QQ 桥（dsh-qq-bridge-mumu）配对，实现「她玩手机时你在 QQ 说话她能看到、能回」。

**设计哲学**（贯穿全部代码）：

1. **零第三方依赖**（除 Pillow）：server 是手写 JSON-RPC 2.0 stdio（`server.py`），不依赖 mcp SDK；HTTP 控制口用 stdlib `http.server`；子进程用 `asyncio.create_subprocess_exec`。
2. **观-想-动循环**：工具设计围绕「先 `screen` 看图 → `ui` 拿可点元素 → `tap` 点 → 返回里自动带回截图确认」。工具返回的图片坐标与屏幕同尺度，模型可以直接按图点坐标。
3. **优雅降级，任何系统不劣于原行为**：触摸注入三级兜底（sendevent → input motionevent → input swipe）；截图多帧走 screenrecord+ffmpeg 失败退连续 screencap；ADBKeyboard 不在就退 `input text`（仅 ASCII）。
4. **收手是硬约束**：`mumu_phone_exit` 必须显式调用才算结束；主人喊停后 `forced=true`，玩类工具直接拒绝，保证主会话释放。
5. **中文标识符**：大量函数/变量用中文命名（`选目标`、`尾巴`、`_触摸按下`、`控制口.处理`），是有意为之（给中文维护者读），grep 时注意。

   │     │     ├── vm/state.py   持久状态 state.json（397 行）

### 2.1 MCP 层（server.py）

- `server.py:60` `McpServer`：`dispatch()`（:113）路由 initialize / tools/list / tools/call / ping；`_initialize`（:71）对不认识的协议版本**回显客户端要的版本**（服务器与版本无关），避免 SDK 断开。
- `server.py:144` `_stdin_reader_thread`：后台线程读 stdin（Windows 上 asyncio 不能直接接管道），`call_soon_threadsafe` 塞进 asyncio.Queue。
- `server.py:214-218`：退出时 `os._exit(0)`（:218）硬退——阻塞的 stdin 线程会在解释器退出时抢 stdout 锁。
- `server.py:164-173`：启动时顺带拉起控制口 `control.启动(端口)` 和调度器 `autoplay.启动()`（都吞异常，起不来不致命）。

### 2.3 本地控制口（control.py，127.0.0.1:8791）

stdlib `ThreadingHTTPServer`，daemon 线程（`control.py:130-138` `启动()`）。全是同步 state 操作，不碰事件循环；只有 `/exit` 关 VM 时用 `asyncio.run_coroutine_threadsafe(svc.phone.stop(), svc.loop)`：115-121，`svc.loop` 由 server.py:176-179 注入。

| 路由 | 行号 | 作用 |
| --- | --- | --- |

| GET /pending | :69 | 未处理挂起消息 |

### 2.4 QQ 桥 ↔ 本服务的闭环

1. 你在 QQ 说话 → QQ 桥检测到「正在玩」（GET /state 的 playing）→ POST /pending 挂起 + 冷却回复。
2. 她每次调任何工具，返回尾巴带 pending 提醒（`pending_notice_text` state.py:322-329）。
3. 回：`mumu_phone_say(msg_id, text)` → POST `qq_say_path`（默认 `/dsh-qq-bridge/say`）→ 真发 QQ。
4. 停：QQ 桥命中停手关键词 → POST /exit → forced=true，玩类工具拒 → 她那回合收尾。

### 2.5 自主玩调度（autoplay.py）

MCP 进程内守护线程，`启动()`（:138）每 `autoplay_check_sec`（默认 60s，夹 15~600）跑 `_跑一轮()`（:74）：

1. 总闸 `autoplay_enable`（默认关）；已在玩 / 距上次触发 <600s 冷却 → 跳过。
2. ① 定时计划到点（`state.due_scheduled()`，10 分钟窗口）；② 闲时判定：活跃时段 `autoplay_active_hours`（`_在活跃时段` :19 支持跨午夜区间）、每日额度/次数、`GET qq_agent_state_path` 问 DSH 是否 running + 距最后用户消息 ≥ `autoplay_idle_minutes`（问不到 DSH **宁可不做**，:126）。
3. 触发 = POST `qq_turn_path`（`_发回合` :55，mode=followup），让 DSH 开一轮，模型自己调 mumu_phone_play。
4. 与 dsh-mumu-up 互斥：装了唤醒器就别开 `autoplay_enable`（README:116），两套同时开会重复叫她。

## 3. 触摸输入：三条路线的演进（最重要的部分）

代码位置：`vm/adb.py:223-332`，类属性缓存 `_触屏节点` / `_触屏节点探测过`（:230-231）。

### 路线一（上游原版）：`input tap / input swipe`

上游 astrbot_plugin_mumu_vm 的 vm/adb.py 就是纯 `input tap/swipe`（CHANGELOG 结论修正节：上游只有 Initial release，不存在"改坏"迭代）。问题：**Android 15 上注入的是带 `TOOL_TYPE_FINGER` 的合成事件，开心消消乐等游戏引擎不认**——点不动/拖不动（CHANGELOG 2026-10-24 第一条）。

### 路线二（过渡）：`input motionevent DOWN/MOVE/UP`

仍是 input 体系，部分游戏依旧不认；现在只做兜底 1（adb.py:317-327）。

### 路线三（定案）：sendevent 原始事件流（MT 协议 B）

**探测触屏节点** `_触屏事件节点()`（adb.py:233-251）：

```bash
getevent -pl 2>/dev/null | grep -B30 INPUT_PROP_DIRECT | grep 'add device' | tail -1
```

- 只探一次，结果缓存；探测过标志 `_触屏节点探测过` 即便失败也置位（避免每次 tap 都跑一遍）。
- `INPUT_PROP_DIRECT` = 真触屏（DIRECT=触屏不是触控板）。**坑（adb.py:238-239 注释）**：设备头行 `add device N: /dev/input/eventX` 与 props 行之间隔着整张事件表，`grep -B8` 抠不到，必须 `-B30`，再正则 `r"/dev/input/event\d+"` 抠路径。
- 本机实测 MuMu Android 15 = `/dev/input/event4`（「Xiaomi Touchscreen」，cap：BTN_MOUSE+BTN_TOOL_FINGER，**无 BTN_TOUCH 常量出现在名字里但协议里用 code 330**）。

**事件序列构造**（sendevent 逐条写 `(type, code, value)`）：

- 按下 `_触摸按下`（adb.py:258-267）：`(3,47,0) ABS_MT_SLOT 0` → `(3,57,tid) ABS_MT_TRACKING_ID` → `(3,53,x) ABS_MT_POSITION_X` → `(3,54,y) ABS_MT_POSITION_Y` → `(1,330,1) BTN_TOUCH DOWN` → `(0,0,0) SYN_REPORT`。
- 移动 `_触摸移动`（:269-270）：`(3,53,x) (3,54,y) (0,0,0)`（slot 已持有 tracking id，无需重发）。
- 抬起 `_触摸抬起`（:272-277）：`(1,330,0) BTN_TOUCH UP` → `(3,57,-1) TRACKING_ID 结束` → `(0,0,0)`。
- **多指**：靠 `ABS_MT_SLOT` 区分触点，每个触点独立 tracking id（当前实现单指，tap 用 tid=99001、swipe 用 tid=99002 只是防混淆）。扩展多指 = 每个 slot 一组 SLOT/TRACKING_ID/X/Y 后共用一个 SYN_REPORT。
- 发送 `_sendevent_touch`（:253-256）：把整个序列拼成**一条 shell 命令** `sendevent 节点 t c v; sendevent …`，一次执行保证时序连续。

**tap**（:279-291）：探测到节点 → 按下+抬起一次发完；异常/无节点 → `input tap`。
**swipe**（:296-332）：`steps = clamp(duration_ms/50, 3, 12)`（50ms/步）→ 按下 → steps-1 个插值 MOVE → 抬起；兜底链 `input motionevent`（输出含 Exception/Error 再退）→ `input swipe`。
**long_press**（:293-294）：同点 swipe（duration_ms 即按压时长）。

**实测验证**（CHANGELOG 2026-10-24 三条合并）：登录页按钮、协议弹窗（「同意」热区偏 ~7px）正常；整机重启后关卡内 sendevent swipe 完成**真实三消**（分数 0→300，步数 22→21）。方案定案，无需再改。

### 6.3 已知坑（具体到命令与报错）

1. **MSYS/路径转换**：在 Git-Bash/MSYS 环境跑 `python -c "open('/c/...')"` 会 FileNotFound——MSYS 路径只有 bash 工具认识，Python 不认（要用 `C:\...` 原生路径）。反过来 adb/MuMuManager 参数里的 Windows 路径在 bash 里也可能被改写。跨 shell 传路径一律写死原生形式或放脚本文件里。
2. **getevent 探测管道坑**：`grep -B8` 抠不到设备头行（头行离 `INPUT_PROP_DIRECT` 隔整张事件表），必须 `grep -B30 INPUT_PROP_DIRECT | grep 'add device' | tail -1`（vm/adb.py:241）。探测结果缓存一次；节点变了要重启 MCP 进程（`_触屏节点探测过` 不重探）。
3. **弹窗点不动 ≠ 注入失效**：开心消消乐「重复创建账号」弹窗全方案点不动，根因是**游戏引擎输入线程卡死**（进程活着但不消费事件）。修法：`am force-stop <pkg>` + monkey LAUNCHER 重启游戏。附带：游戏按钮**热区可偏 10~20px**（「同意」比视觉低 ~7px），点不动先用坐标网格扫描找热区（CHANGELOG 2026-10-24 补充节）。
4. **新手引导吞输入**：另一复现根因——引导模式吞注入事件，跳过引导即恢复。
5. **qq_say_path 旧前缀 404**：默认已是 `/dsh-qq-bridge/say`；老配置文件里若还是 `/dsh-qq-bridge-mumu/say` 会「发不出去」（mumu_phone_say 404）。
6. **status 会把刚关的 VM 复活**：`h_status` 只在 mode.active 时 ensure（tools.py:222-224）；改这段逻辑时别把这个保护改掉。
7. **pending 3 小时过期是硬编码**：`vm/state.py:311` `cutoff = time.time() - 3 * 3600`，`pending_max_age_hours` 配置项目前没接线。
8. **`close_mumu_app_on_exit` 杀两遍**：`cleanup`（mumu.py:307-336）两次 kill_processes——部分组件会被重新拉起，别「优化」掉第二轮。
9. **录屏绕锁**：`screen_record(..., locked=False)`（adb.py:502-515）有意绕开全局 adb 锁，让录屏同时能注入操作；不要改回加锁。
10. **DDH 工具宿主清洗环境变量**：`*KEY|*PASSWORD|*SECRET|*TOKEN*` 与 `DSH_*` 会被宿主剥掉，再合并 DSH 挂载配置里的 env（README:53）——往 env 里塞令牌传不进去。
11. **tests 硬编码路径**：test_client.py:7-8、test_pending.py:10-13 写死 `D:\EX\dsh\mumu-mcp` 旧位置，换机先改。
12. **MCP 协议版本**：`_initialize` 对任何 `20xx-xx-xx` 版本都回显接受（server.py:76-79）；若换成真 SDK 宿主，靠这个兜底不断连。
